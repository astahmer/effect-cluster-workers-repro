# Effect Cluster Worker proof: capability parity with Emisoup

Checked 2026-10-09 against the Emisoup checkout and the local PostgreSQL proof. The tracked proof pins `effect@4.0.2` and `@effect/sql-pg@4.0.2`; Emisoup currently pins `4.0.0-beta.107` for Effect, SQL-Pg, and platform-node.

## Differences that matter

### Transport and Worker runtime

Emisoup's `NodeClusterSocket` uses a Node socket server for runner RPC. Cloudflare's current Worker protocol docs list outbound direct TCP sockets but no inbound TCP listener, so this server transport cannot run inside a Worker today. The Worker proof therefore uses `HttpRunner.layerHttpOptions` and `HttpRunner.layerHttpClientOnly`, with a fetch shim that routes runner hostnames to named Durable Objects. This proves Effect Cluster's HTTP runner protocol, sharding, and inter-runner RPC through DO bindings. It does not prove the Node socket transport or that a Node runner process can run inside Workers. See Cloudflare's [protocol support](https://developers.cloudflare.com/workers/reference/protocols/), Effect's [Node cluster socket API](https://effect.website/docs/v4/api/platform-node/NodeClusterSocket/), and Effect's [Node cluster HTTP API](https://effect.website/docs/v4/api/platform-node/NodeClusterHttp/).

The beta `NodeClusterSocket` implementation defaults to MessagePack. The Worker adaptation uses JSON on its HTTP runner and client layers: a prior Worker trial with MessagePack hung during workflow dispatch, while the JSON configuration passed the replay and interruption proofs. Keep the Worker runner/client RPC configuration homogeneous; mixed Node-socket and Worker-HTTP interoperability was not tested.

The two runners are named Durable Objects in one Worker script, not two independently deployed Node processes. Wrangler restart verifies local Durable Object storage and PostgreSQL state reconstruction. A local `ctx.abort()` test now resets one specific runner during an in-flight workflow Activity while leaving the Worker process up. The surviving runner takes over all 32 shards after lease expiry; the reset runner later reconstructs and rejoins. This does not exercise Cloudflare's cross-region placement or independent production Worker deployments. See Cloudflare's [Durable Object state API](https://developers.cloudflare.com/durable-objects/api/state/) for the reset behavior used by the test.

### PostgreSQL and Hyperdrive

`wrangler.pg.toml` has a placeholder Hyperdrive ID. Local `wrangler dev` uses `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_CLUSTER_DB` to connect directly to the disposable PostgreSQL database. Cloudflare documents that this local mode bypasses Hyperdrive connection pooling and query caching; a real Hyperdrive path has not been exercised here. See [Hyperdrive local development](https://developers.cloudflare.com/hyperdrive/configuration/local-development/).

The Worker proof sets `shardLockDisableAdvisory: true` and verifies row-based shard leases. Cloudflare lists PostgreSQL advisory locks as unsupported by Hyperdrive, so the Worker-specific setting is required for that target. Emisoup's current VPS setup does not use this local Hyperdrive path. See [Hyperdrive's supported PostgreSQL features](https://developers.cloudflare.com/hyperdrive/reference/supported-databases-and-features/).

The local setup uses four PostgreSQL connections per runner/client layer. This is not a measurement of connection use through a production Hyperdrive pool or at Emisoup's full runner count.

### Application behavior not reproduced

The proof uses one synthetic counter workflow. It does not load Emisoup's real task registry, `TaskWorkflowLifecycle`, Twitch/YouTube/TikTok workflows, application repositories, provider clients, actors, crons, task reaper, or API proxy. The sample startup recovery only processes up to 20 active rows; it does not implement Emisoup's stale-task cleanup, unsupported-task handling, 200-row reconciliation page, or startup retry policy. Emisoup also has runner-storage refresh observability and application-specific task lifecycle/error handling that this proof does not include.

The proof kills the runner after its PostgreSQL transaction commits but before the Activity returns. Replay runs the Activity a second time; a PostgreSQL operation ledger keyed by the stable workflow operation ID prevents a duplicate counter update. The task is completed after recovery. This verifies at-least-once Activity replay with an idempotent SQL effect, not exactly-once external effects. Provider calls, emails, and other remote side effects still need provider idempotency keys or an outbox/deduplication boundary. Effect documents that only completed Activity results are memoized and that an interrupted Activity body can run again; see the [Activity reference](https://effect.website/docs/v4/api/effect/workflow/Activity).

The tracked release proof uses SchemaBinary, which Effect documents as the binary RPC encoding. Its API is `RpcSerialization.layerSchemaBinary(options?)`, so the layer must be called. The beta package uses the `effect/unstable/...` import paths and `RpcSerialization.layerJson`; the release package uses `effect/...` and SchemaBinary. See [Effect RPC serialization](https://effect.website/docs/v4/api/effect/rpc/RpcSerialization/).

The tracked `4.0.2` run and a temporary compatibility copy on Emisoup's exact `4.0.0-beta.107` both passed the targeted DO interruption and post-commit Activity replay. The beta run used the installed beta packages, beta import paths, JSON RPC serialization, Wrangler `4.148.0`, a fresh local Worker persistence directory, and a dedicated PostgreSQL schema inside the local repro database. Its output showed runner-1 reset, runner-0 taking all 32 shards, two Activity attempts, one effect, task `complete`, workflow `Complete`, and 16/16 ownership after rejoin. The temporary schema and scratch copy were removed. This closes the beta-specific interruption gap for the HTTP Runner adaptation; it does not prove `NodeClusterSocket` or Hyperdrive behavior.

## Local evidence and repeatable command sequence

The tracked setup uses `effect@4.0.2`, `@effect/sql-pg@4.0.2`, Wrangler `4.148.0`, and the ignored `.pg-repro.env` connection string for the dedicated local database `effect_cluster_workers_repro_20261009`.

1. Start `pnpm dev:pg` with the environment in `.pg-repro.env` loaded.
2. Run `pnpm prove -- http://localhost:8790`. It checks 32 shards, 16/16 ownership, runner-0 ingress to runner-1 execution, mailbox request/reply, a replayed workflow result, a completed poll, and the PostgreSQL activity counter.
3. Stop Wrangler and start it again with the same local persistence path and PostgreSQL database.
4. Run `pnpm prove -- http://localhost:8790 --require-existing`. It requires previous mailbox and DO counter rows, verifies the same workflow result, and checks that the staged task was recovered after runner initialization.
5. Run `pnpm prove:runner-recovery -- http://localhost:8790`. This interrupts one runner during an Activity, waits for lease expiry, and verifies retry and rejoin without restarting Wrangler.
6. Stop Wrangler and run `pnpm prove:mailbox`. This exercises concurrent claims, stale claim release, delayed delivery, and reply cleanup.
7. Run `pnpm exec wrangler deploy --dry-run --config wrangler.pg.toml`. This checks bundling and binding configuration only; no deployment was performed.

Stable-package results from the final run:

- Initial proof: `runner0Owns=16`, `runner1Owns=16`, `executionRunner=runner-1`, workflow result `1`, workflow replay `1`, and no pre-existing recovery task.
- After restart: the DO counter advanced from `25` to `26`; the workflow result and PostgreSQL activity counter stayed at `1`; the task status became `complete` with result value `1`.
- Runner-only interruption: runner-0 was reset after the PostgreSQL effect committed; runner-1 held all 32 shards after lease expiry; the Activity ran twice but the operation ledger and counter each stayed at one effect; the task completed after runner-0 reconstructed; final ownership returned to 16/16.
- Fresh task replay: after staging task `workers-repro-startup-recovery-proof-v6`, Wrangler was stopped and restarted; `pnpm prove -- http://localhost:8790 --require-existing` found the task complete with result value `1`, while the stable workflow still had one Activity attempt and one effect.
- Mailbox proof: 66 unique eligible concurrent claims, batch maximum 64, 64 claims recovered after the lock was released, one stale claim recovered, one delayed message delivered after its due time, and two messages released after reply cleanup.
- Dry-run: passed. It does not validate real Hyperdrive credentials, pooling, network access, or deployed DO recovery.

## Next minimal proofs

1. Hyperdrive pooling and caching remain unverified. Local `wrangler dev` connects directly to PostgreSQL and bypasses Hyperdrive; exercising the real service requires a Cloudflare-backed Worker and a disposable database. Keep this as a later isolated deployment check, never point it at production. See [Cloudflare's local-development modes](https://developers.cloudflare.com/hyperdrive/configuration/local-development/).
2. If Worker hosting remains a target, port one actual Emisoup workflow and its task resolution contract into the Worker bundle. Keep Node TCP and Worker HTTP transport results separate.
3. Test real external-provider idempotency and cancellation semantics before moving provider-backed workflows; the synthetic PostgreSQL operation ledger does not prove those remote contracts.
